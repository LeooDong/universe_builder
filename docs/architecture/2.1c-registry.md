### 2.1c Registry and operations — `src/universe_builder/atoms.py`, `config.py`, `operations/`

Split out of `execute_prompt.py` so the operations can be imported without
importing the orchestrator — the orchestrator calls them, so the dependency runs
one way only.

- **`registry.py`** — the one declarative atom registry. `AtomSpec`/`ExpandSpec`/
  `AppendSpec` declare an atom once; a `DomainPack` groups the specs for a problem
  domain plus its index atom (the seed that lists work). `active_pack()` is the
  source of truth; a second domain is a new pack, never an edit to core. See §6.
- **`atoms.py`** — `class_mapping`, `atom_mapping` and the stage-model registry
  (`STAGE_MODELS` + `resolve_stored_class`), all **derived** from `active_pack()`
  rather than hand-written. `resolve_stored_class` answers "what model matches the
  payload actually on disk", not always the canonical model for the atom type.
  See §7 on multiple on-disk shapes.
- **`config.py`** — `OperationConfig`, `llm_call_mapping`, `PHASE_MODELS`, and the
  placeholder-free operation instructions. `pipeline.yaml` is meant to replace
  most of it; keeping it as plain data makes that a transcription.
- **`operations/`** — one module per operation, each returning a `Result`.

**`Result` is what makes a failed operation safe.** Every `process_*_operation`
used to return a JSON *string*, and each caller decided whether it had worked by
re-parsing it and asking `is_empty_model` (now `store`'s). Success and failure
shared one channel, so telling them apart was optional — and two call sites did
not bother, which is what B8 was. `Result.outcome` is one of `OK`, `SKIPPED`,
`INVALID` or `FAILED`; `Result.should_write` is true only for `OK` with an atom
attached, so a caller cannot write a sentinel by forgetting to look.

The `INVALID`/`FAILED` split matters: `INVALID` means the model answered and the
answer did not fit the schema, so there is a payload worth keeping as evidence,
whereas `FAILED` means nothing usable came back. `SKIPPED` is a success — a
re-run of expand over a finished file must not look like an error, and must not
rewrite the file.

**An operation that rewrites an atom in place says so** (v0.3.2):
`result_from_call(..., replaces=path)` keeps the bytes at `path` with the
attempt when the result validated, before the caller writes. Verify, create
and append pass `call.response_path`; fix passes nothing (`commit_fix` never
writes over an atom); expand's per-entry calls pass nothing and its single
write goes through `operations.expand.write_expanded`, which journals one
`splice` line keeping the city's bytes — the sync pass and batch collect's
`apply_expansions` both use it; `operations.merge` journals the append merge
the same way. §2.1e has the table and `restore`.
