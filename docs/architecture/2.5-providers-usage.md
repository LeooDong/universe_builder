### 2.5 Provider layer, continued — using it

#### One call

```python
from universe_builder.providers import get_provider
from universe_builder.providers.requests import build_request

request = build_request("person", "Genghis Khan", "claude-sonnet-5")
response = get_provider(request.model).complete(request)

if response.ok:
    print(response.parsed.name.common)
    print(response.usage.cache_read_tokens, "tokens read from cache")
else:
    print("validation failed:", response.error)
```

`complete()` from `providers.run` adds retries — including a re-ask on schema
failure, which is cheaper than letting the file fall through to the fix pass.

#### Reasoning effort (v0.6.0)

`LLMRequest(effort=...)`, `pipeline.yaml`'s `effort:` block, or `--effort` on
`run` and `run_batch submit`. One provider-neutral level, translated per
provider (`providers/effort.py`):

| | sent as | levels | when it is not sent |
|---|---|---|---|
| OpenAI (Chat Completions, every batch line) | `reasoning_effort` | low, medium, high; xhigh only for a model whose row lists it in `effort_levels` (none yet: unverified) | `effort: false` models (gpt-4o-mini, gpt-4.1, gpt-4.1-mini): not reasoning models |
| OpenAI `/v1/responses` | `reasoning: {effort}` | the same | the same |
| Anthropic (streamed and Message Batches) | `output_config.effort`, beside `output_config.format` | low, medium, high, xhigh, max | Haiku 4.5 (`effort: false`: the API refuses it) |
| Google, DeepSeek, Qwen, OpenRouter | nothing (warned once per model) | — | always |

**Unset sends nothing**, and the request is byte for byte what it was before
v0.6.0. That is the comparison problem this solves: without it, OpenAI's
reasoning models ran at the API's default reasoning effort (the default is not
recorded in this repo; check OpenAI's documentation for the model) and Claude
at the model's default (`high` on Haiku 5.5 and Sonnet 5.5, `medium` on Opus
5.5), so two vendors were never compared at a stated effort. A level a
model lacks (`max` on OpenAI; `xhigh` on an OpenAI model with no row listing
it) is refused, never mapped to a neighbour: the
CLI refuses it before the first call, and `EffortNotSupported` (a 400 to
`run.complete`, so not retried) if a request reaches a provider anyway.

**What is recorded is the effort sent, not the one asked** (`effort.sent`):
journalled as `sent_effort`, stamped on batch handles (`extra["effort"]`) and
on experiment replies; a request to a provider or model that takes none is
recorded as none. `run.json` records the run's setting when one is set, and
`costs --by effort` splits a model's spend by what was sent. Prompt experiments take it per arm
(`--effort-a`, `--effort-b`) and per judge (`experiment judge --effort`);
ARCHITECTURE §2.1g. No live run has measured what effort does to cost or
quality yet: the output-token estimates in `experiment replay`
are nominal.

#### Task budget (v0.6.1)

`LLMRequest(task_budget=N)`, `pipeline.yaml`'s `task_budget:` block, or
`--task-budget N` on `run` (every phase, sync and batch) and `run_batch
submit`; `providers.task_budget.add_argument` gives a pack's own verb the
same flag. It is Anthropic's task budget (beta `task-budgets-2026-03-13`):
`output_config.task_budget = {"type": "tokens", "total": N}`, merged beside
`output_config.effort` and `output_config.format`.

| | sent as | when it is not sent |
|---|---|---|
| Anthropic, streamed (and the prompt-only fallback) | `client.beta.messages.stream(..., betas=["task-budgets-2026-03-13"])` | never silently: refused (below) |
| Anthropic, Message Batches | `client.beta.messages.batches.create(betas=[...], requests=[...])`, each line's `params.output_config.task_budget`; the handle records `extra["betas"]` and is polled and collected through the beta batches endpoints | the same |
| OpenAI, Google, DeepSeek, Qwen, OpenRouter | nothing (warned once per model): no equivalent | always |

**Unset sends nothing**: the request, the endpoint and the handle are byte
for byte what they were before v0.6.1.

**Refused before the call** (`TaskBudgetRefused`, a 400 to `run.complete`,
never retried; the CLI refuses the run up front with `task_budget.refusal`):
a total under 20,000 (the API's minimum; the flag and the config refuse it
on parse); a Claude model whose `model_pricing.json` row lacks
`"task_budget": true` (marked: Fable 5.1, Opus 5.5, Opus 5, Opus 4.8,
Sonnet 5; not Sonnet 5.5, Haiku 5.5 or Haiku 4.5); and a total over the
`max_tokens` the request sends (held to the model's output cap). That last is
the single-turn rule: every engine call is one response, which can never
spend more than its `max_tokens`, so a budget above it would have the model
pace itself for room it does not have. An agent loop a pack drives itself,
where one budget spans several responses, sets
`LLMRequest.allow_task_budget_over_max_tokens=True`.

**How to size it.** The budget is advisory: the model sees a countdown and
plans to finish inside it, and `max_tokens` stays the hard cap the model does
not see. Size it by measuring the task (the output tokens a good reply takes
at the effort you run), not by guessing. For a single call keep it under
`max_tokens` with headroom, one half to two thirds of it, so a reply that
overruns its plan still lands before the cut-off (over two thirds is allowed
and warned once). Note the engine's bare `DEFAULT_MAX_TOKENS` (16,384) is
under the minimum, so a budget needs `pipeline.yaml`'s 32,768 or more beside
it. Live, a request at effort `high` with a budget well under `max_tokens`
finished early (`end_turn`); the same kind of request with no budget thought
through its whole output allowance and was truncated. A Message Batch
carrying a budget was accepted too.

**Recorded as sent** (`task_budget.sent`): `sent_task_budget` on journal
attempt lines, `extra["task_budget"]` on batch handles, `task_budget` in
`run.json`'s config, each only when one was sent; none for a provider that
ignores it. Prompt experiments take none yet (`run --experiment` with a
budget is refused; ARCHITECTURE §2.2b).

#### Batch

Submit and collect are separate commands because a batch can take 24 hours. The
handle is written to `data/automated/_batches/` and works from any later process.

```bash
# After installing from the repo root: python -m pip install -e .

python -m universe_builder.run_batch models                                    # pricing table
python -m universe_builder.run_batch estimate --atom person --model gpt-5-nano --count 5000

python -m universe_builder.run_batch submit --atom person --model gpt-5-nano --from-history
python -m universe_builder.run_batch list
python -m universe_builder.run_batch poll --all
python -m universe_builder.run_batch collect --all          # writes .json and .json_ERROR files
python -m universe_builder.run_batch cancel --all [--apply]  # stop running batches; finished results stay collectable
```

`collect` writes valid results as `.json` and schema failures as `.json_ERROR`,
so your existing fix pass picks them up unchanged. Filenames use the same
`fileName` convention, with the sequential ID taken from the batch `custom_id` —
which means batch filenames are **stable across reruns**, unlike the sync path's
process-local counter.

**Results are reconciled against what was submitted.** A schema failure is a
recorded failure; a result that never arrives at all is a silent loss, and the
two need different handling. `collect` tracks every returned `custom_id` against
the submitted set, reports `report.missing`, writes the full list to
`_batches/missing/<handle>.json`, and `run_batch.py collect` exits non-zero.
`run_batch.py list` shows any incomplete batches underneath the handle listing.

The report goes in a `missing/` **subdirectory** rather than beside the handles
for a reason worth stating: an earlier version wrote `<handle>.missing.json`,
which matched the `*.json` glob that finds batch handles, so a single incomplete
batch broke every later `list`, `poll --all` and `collect --all` with a raw
`TypeError`. `load()` now also rejects non-handles with a clear message and
`list_batches()` skips them, so a stray file in that directory is a warning
rather than a crash. Three ways
results can go missing, all now covered:

- **OpenAI puts API-level failures in a separate error file.** Requests rejected
  for bad input or rate limits never reach `output_file_id`. Reading only the
  output file means those requests vanish with no trace — submit 5,000, collect
  4,800, and nothing tells you about the 200. `fetch_batch_results` now reads
  `error_file_id` too.
- **A batch can end terminally with no output file at all.** Both the OpenAI and
  Google providers now emit one failed `LLMResponse` per submitted request in
  that case, rather than returning an empty iterator.
- **A Gemini job can fail at the job level**, which previously logged an error
  and returned nothing.

#### From the existing pipeline

`ProviderCall` / `ProviderCallAugment` keep the `LLMCall` contract, so they drop
into `llm_call_mapping` with no other changes to `execute_prompt.py`:

```python
from universe_builder.llm_classes.provider_call import ProviderCall, ProviderCallAugment

llm_call_mapping = {
    "gpt-5-nano": ProviderCall,
    ("gpt-5-nano", "augment"): ProviderCallAugment,
    "claude-haiku-4-5-20251001": ProviderCall,
    ("claude-haiku-4-5-20251001", "augment"): ProviderCallAugment,
}
```

One pair covers every provider, because the provider is resolved from the model ID.

#### Adding a provider

1. Subclass `Provider` in `src/universe_builder/providers/`, implement `complete()`, and add the
   three batch methods if there's a batch API.
2. Add a factory line to `_FACTORIES` in `registry.py`.
3. Add the models to `model_pricing.json`.

#### Concurrency and caching interact

`run_many(concurrency=N)` issues one request first, then parallelises the rest. A
cache entry only becomes readable once the first response starts streaming, so
firing N identical-prefix requests at once means all N pay full price. Warming
with a single call first is worth roughly the prefix cost × (N−1).

#### Caveats

- **Pricing goes stale.** `model_pricing.json` was checked by hand and
  carries a `_comment` saying when. `estimate_cost()` returns `None` for unlisted
  models rather than guessing.
- **Verify the OpenAI and Google model IDs.** I took `gpt-5-nano`, `gpt-5.6-luna`,
  `gpt-6-astra` and the Gemini IDs from current pricing pages, but IDs are easy to
  get subtly wrong. Check against `client.models.list()` before a large run — a
  wrong ID is a 404, which is at least loud.
- **Google batch is untested against a live key.**
- **`prefix_tokens()` is a character-count heuristic** (~4 chars/token). Fine for
  "am I above the cache minimum", not for billing. Use `count_tokens` if you need
  precision.
- **Effort has not run live** (v0.6.0): the wire shapes follow each vendor's
  documented parameter (`reasoning_effort`, `reasoning.effort`,
  `output_config.effort`) and are pinned offline; a one-request smoke on each
  provider is worth doing before a paid experiment relies on them.
- **The task budget's sync path has not run through the engine live**
  (v0.6.1): the request shape was checked by hand against the API
  (a sync call and a batch submit, above); the engine's wire is
  pinned offline against the SDK's beta signatures. Polling and collecting a
  beta-submitted batch through the beta endpoints is unverified live.
- **Anthropic ran live** (v0.5.9): the smoke test, sync creates on
  Haiku 4.5 and 5.5 through a pack that installs this engine, a small Message Batch, and a deliberate
  truncation on both paths. The ids came from `client.models.list()`.
