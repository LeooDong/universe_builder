### 2.3 Orchestration — `src/universe_builder/execute_prompt.py`

The registries are **derived from the active `DomainPack`** (`registry.py`), not
hand-written, so adding or reshaping an atom is one `AtomSpec` edit:

- `class_mapping` — class name → Pydantic class (seed/index/expanded/append models).
- `atom_mapping` — atom name (incl. `expand_*`/`append_*`) → `AtomMapping(atom_class,
  prompt_start_text, example_json_file, plural)`, rebuilt in place by
  `atoms.reload_from_pack()` on a pack switch.

`llm_call_mapping` (model version → call class; keys are either a bare string for
create or a `(model, "augment")` tuple for fix/verify/expand/append) is a separate
registry that derives from the tier tables in `pipeline.yaml` (`config.py`), **not**
from the pack. It is never edited by hand: adding a model is a `pipeline.yaml` edit,
and adding a provider is a `providers/registry._FACTORIES` entry plus a pricing row —
never a new `LLMCall` subclass. See §2.5.

`OperationConfig` is the per-pass parameter object: atom name, model version, system
text, operation type, and the expand-specific fields (`subatom_to_expand`,
`expander_class`).

Two drivers:

- `call_and_save_prompt(config, topic_list)` — create pass. Loops topics, builds a call,
  writes the file. Exceptions are logged and skipped so one bad topic cannot end a run.
- `augment_and_save_prompt(config, limit=None, concurrency=None)` — every other pass.
  Lists the atom folder and keeps only the files the operation acts on (`fix` sees
  `_ERROR` sentinels, `verify` sees valid atoms, `expand`/`append` see both with
  sentinels first), reconstructs the topic from the filename, and
  dispatches on `config.operation_type` to `process_fix_operation`,
  `process_verify_operation`, `process_expand_operation` or `process_append_operation`.
  An atom type with no folder yet is no work (v0.1.20; it
  used to raise `FileNotFoundError` and end a run over every atom type).
