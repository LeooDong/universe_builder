### 2.1f-ii Cross-references — `src/universe_builder/index.py`, `universe_builder index`

**Never store what you can derive.** An atom does not record which Histories
list it — the History atoms *are* the membership edges, and a stored
`civilisations:` field would go stale the moment a third History lists the atom
or the atom regenerates. Name fields (`notableFigures`,
`discoverorOrInventor`, a person's `spouses`) stay free text at generation
time, because models are good at names and would hallucinate ids. `universe_builder index`
turns both into edges after the fact, writing
`links.json` under `data/automated/<domain>/_index/` (machinery, underscore-skipped, always
recomputable): `memberships` (per civilisation, per atom type, each listed
subject and the atom it resolves to — None marks listed-but-never-generated),
`references` (resolved name links, declared in `active_pack().link_fields` — extending
a relation is one line there), `unresolved` (names nothing on disk answers
to; report material, not errors), `duplicates` (names two stored atoms both
declare — see §2.1f-iii-a), and `provenance` (each atom's ordered write
history from the journal). `index.memberships()` computes the first section
alone, without the reference walk, and equals `build()["memberships"]`
(v0.2.0; the history pack's fold-history and retire-list
gates kept a copy of the loop until then).
**A pack may resolve memberships** (v0.4.1): `DomainPack.membership_resolver`,
given the raw memberships (one context per stored index atom), returns the
memberships every reader sees and a record of what it changed, which `build`
writes as `links.json`'s `folds` section (only when non-empty, so a pack
without one builds as before). `index.memberships()` returns the resolved view;
`memberships(resolved=False)` what each index atom literally lists. History
uses it for folds: a folded line keeps its own index atom, so it can be unfolded,
and the resolver files its members under the lines it folds into.

**A link is declared as a wire *path*, and the path is validated at pack
registration.** Dotted for nested models (`birth.location.city`), `[]` for a
list of objects (`cityPeriodsOfHistory[].tradingPartners`); a bare field name
is a one-segment path, so older declarations are unchanged. **The `[]` marker is
validated against the field's real shape**, in both directions: a marker on a
field that is not a list, and a missing marker on one that is, each validate
trivially and then yield *zero* edges at read time — traversal meets a list
where it wants an object, or the reverse — which is the same silent failure the
`person` relations suffered. Each edge carries
`at`, the occurrence with list indices filled in, so a consumer can say which
period made an assertion rather than only which atom did.

The validation is not tidiness. `index.build` reads a path off a raw payload
dict, where **a field that does not exist and a field that is empty are the
same answer** — so the four `person` relations, declared flat as `parents`,
`children`, `spouses`, `otherRelatives` while the model has always held them
under `family`, produced *zero* edges from every stored mention for as long
as they had been declared, and nothing anywhere reported a problem. Registration
is the last moment that mistake is still cheap, so `register_pack` walks every
path through its **source** model — through `stages` and the expand spec too,
since a city is `City` before expansion and `CityExpanded` after — and raises
naming the segment and the shapes it searched. Correcting those four paths and
declaring the undeclared `location.city` paths multiplied the corpus's
resolved edges several times over. Provenance is the answer to stale `certainty`:
that field is a model's *truth-confidence* self-assessment and nothing more,
and reading edit-history into it is what made it "stale" when a later model
rewrote a field. Who wrote an atom, when, and through which operation is
orthogonal, lives in the append-only journal, and is never stale — a period
whose government was set by `adjudicate` or rewritten by `split`/`fix` shows
that operation in its atom's history, and `certainty` answers only for itself.

Resolution goes through `topics.subject_resolver` — one resolver, the same
grouping/alias/prefer-stored machinery as the work list — and it resolves **in
the company of every History-listed spelling**, which is not an optimisation:
`Abydos (Abdju)` only finds the atom stored under bare `Abydos` because
another History lists that spelling, and bare `Narmer` only reaches
`Narmer (Menes)` the same way. The first real index run left listed
subjects dangling for exactly this reason; with company, every one
resolves. A context-free name that two groups claim (`Thebes` once Greek
history exists) resolves to None rather than a guess — linking the wrong city
silently is the merge-a-city failure one layer up.

**Speed** (a large corpus went from tens of minutes to seconds, answers
unchanged by the corpus-parity harness): `build` and
`memberships` run inside `store.read_snapshot`, so `atoms_for` answers from one
folder listing per type instead of a glob per question (a pure read: a write
inside the block is not seen; the listing is the calling thread's own, a
context variable, so overlapping builds in two threads cannot share or leave one); `_resolver` keeps each `(type, name, context)`
answer for the build; `name_key` and `alias_keys` are cached as the pure
functions they are; and the resolver's last-resort grouping is handed only the
alias-file lines that share a folded key with the name, in file order, where it
used to rebuild every line's declarations per call.

**Last of all, the resolver reads the names the stored atoms declare about
themselves** (`topics.stored_name_claims`): `name.common` and
`name.otherNames`, folded, mapped to the id taken *from the filename* — never
from hashing a declared name, which for a duplicate would mint a different
atom's id. Keys are exact folded spellings on the claiming side, so a stored
`Ancient Salamis (Cyprus)` does not annex the bare key `cyprus`; the querying
side may still widen a probe, most specific first.

Two properties make this safe. **Claims are terminal** — a claim yields an id
and stops, and a grouping's *survivor* is never looked up in the claims map,
because `mention -> History survivor -> another atom's alias` composes two
declarations, which is the Saqqara chain in a new place. And **claims are
consulted only after every other step has declined**, so the new index can turn
a None into an id but never an id into a different id: rebuilding the real
corpus lost and retargeted none of its pre-existing edges. The cost
of that ordering is recorded rather than hidden — references whose names two
stored atoms claim keep resolving as they did, instead of becoming ambiguous,
because the History machinery answers first. Tightening that needs the resolver
to distinguish *missing* from *ambiguous*, which it does not: `None` means both.
