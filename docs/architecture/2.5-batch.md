### 2.5 Provider layer, continued — batching

**Batching a phase.** `universe_builder run --phase <p> --batch` submits a pass as batch work
instead of running it synchronously; `run_batch collect --all` writes the results.
`cli.BATCHABLE_PHASES` is `index`, `create`, `fix`, `verify` and `expand`. `append` stays
out — it produces a *separate* file that `merge_helper` later pairs with the
original, so its result is not a write-back to a known target.

**`index` via batch** (it was refused before). `cli._submit_index_batch`
takes `work.select_work("index", …)` — the seeds `_run_history` would generate,
so a seed with an index atom is skipped and `--limit` caps seeds — and submits
one batch per seed (each seed is its own context, as create batches per
context), on the index phase's model (frontier) and `max_tokens("index")`.
Requests route `operation="index"`; there is no operation text by that name,
so the prompt is create's, and `collect` writes each atom to
`store.path_for(index, None, seed, model)` through the create branch
(validation, `_ERROR` on failure, journal with usage and the batch-discounted
`estimated_cost`), which `costs --by phase` shows as `index (batch)`. The
request equals the synchronous index call's (`_run_history` → `create_atom`:
persona-only system text, no context line, the seed's unscoped create note
after the subject, the same example, schema and budget) except for the
routing `tests/test_index_batch.py` names: (1) `custom_id` (sync: the subject;
batch: `history-00000-<slug>`); (2) batch metadata adds `operation: "index"`.
Until the two prompt builders became one, sync also quoted the subject as `f"{start} '{subject}'"`,
which that test normalised; both are now built by `requests.build_request`.
`run_batch submit --from-history` still reads the create work list, which
holds no index atoms.

`create` needs only a subject — the destination follows from it, because ids are
content-addressed. `fix` and `verify` rewrite *a particular file*, and that file's
model version, decorations and `_ERROR` state cannot be rebuilt from the subject:
`store.path_for` would reconstruct a plausible path, not the one the payload came
from. `requests.BatchItem` carries `payload` (into the volatile user turn) and
`target` (a path relative to the data directory, recorded in the handle's
routing), and `_output_path` honours the target when present. A target that
resolves outside the data directory is refused and logged — a handle is a file on
disk and could say anything.

**`expand` is the fan-out case, and the shape the others are not.** One city
becomes *many* requests — one per still-unexpanded period — all sharing the
city as payload and the city's path as `target`, each tagged with its
`period_index` in `BatchItem.routing`. `collect` recognises `operation ==
"expand"` and, instead of writing per response (the reply is a single
`Population`, and the target is the whole city — a naive write would replace
the city with one period), accumulates the replies by target and splices each
city once at the end via `operations.expand.apply_expansions`. Under
`store.path_lock(target)`, that splice re-reads the file and places replies only
where their original names remain unexpanded; the index is a hint, not identity.
Sync expand holds the same lock over its read/modify/write. These are in-process
locks, not cross-process transactions. An all-failed sync expansion returns
`FAILED` and never rewrites the file; partial success persists real progress. `submit`/`prepare_expansion`/`splice_expansion` are shared
with the sync path, so both agree on B7 (build the expanded class, never the
seed) and on which periods still need work.

**Failed batches preserve both valid atoms and existing sentinels.** `collect`
uses `store.write_error(..., preserve_existing=True)`: under the target lock it
refuses a sentinel beside an existing atom, then uses `write_new` (`O_EXCL`) to
preserve an earlier sentinel against racing collectors. Failed verify/expand,
and any failure whose target exists, have no journal `work_status`; the raw
failure remains recorded without scheduling destructive repair work.

**One work selection** (v0.1.20). `work.select_work(phase,
atom_type, limit) -> [WorkItem]` is the one answer to "what does this phase act
on": `cli._plan` (the dry run), the create, payload and expand batch
submitters, `execute_prompt.augment_and_save_prompt`, `_run_create`,
`_run_history` and `run_batch submit --from-history` all call it. A work item
is a subject (index, create) or a file (fix: sentinels; verify: atoms; expand:
atoms with entries left; append: atoms), never an `{"error": ...}` placeholder;
fix also lists the sentinels `reconcile_fix_queue` would restore from the
journal (`_support.fix_queue_targets`, shared, read-only). `--limit` caps items
per atom type; a limited expand batch takes N files and asks for every pending
entry of each. Before, the dry run limited fix/verify/expand in total, read 0
as "no limit" (as `run_batch submit` did), counted verify placeholders and
missed restorable sentinels; `run_batch submit --from-history` sent every
subject under one `--context` (now one batch per context, and `--context` is
refused with `--from-history`).

**The index atom type is no file phase's work unless named** (after
v0.3.0; an end-to-end test found `run --phase verify --limit 1 --dry-run`
listing a `history_…` atom). `select_work(..., explicit=False)` returns nothing
for the index atom type in fix, verify, expand and append (`work.takes`); the
CLI passes `explicit=True` only when `--atom` named the type, and so do
`run_phase` and `augment_and_save_prompt`, which skips the fix pass's journal
restore along with it (it writes). Named, `verify` is still refused
(`work.index_refusal`; `select_work` raises, `cmd_run` exits 2 before any
model is resolved): it would re-ask every index atom on another tier and
rewrite, in place, the list every other atom type is generated from — an
index atom is replaced by retiring it and running the index phase. `fix
--atom <index>` repairs a failed index generation's sentinel as before. The
batch submitters already skipped the index type for every phase but `index`.

**One submit loop.** Every batch submitter builds `(label, submit)` groups and
runs them through `work.submit_groups`: a group that raises (a provider
rejecting a batch, a provider without batch support) is recorded and the
others still go, and `cli._report_submission` prints the handles submitted
beside the groups that were not, exiting 1 unless every group went. Before, the
exception left the CLI after earlier groups had been submitted, with no report.

Payload batch submit filters filenames by the selected atom prefix, skips
unparseable filenames, and caps the submitted count at `--limit` per atom type.
An `append_city_*` supplement in the city folder is never submitted as a City.
Unknown schemas, wrong-domain handles and schema mismatches are refused per
handle with an `UNIVERSE_BUILDER_DOMAIN` diagnostic; `collect --all` continues to the rest.

Create batches are split one per `(atom type, context)`, since the context is in
the cached prefix. Payload batches are split per atom type only: what varies
there is the payload, which is volatile by construction, so one prefix already
covers every request for a type.

**Batch chunking honours two limits, not one.** Every batch line carries the whole
prompt — system text, schema and examples — so the byte cap binds long before the
request-count cap. At the current `Person` prefix an OpenAI line is ~26.5 KB, which
puts roughly 7,700 requests in a 200 MB batch rather than the 50,000 the count
limit would allow. `Provider.chunk_for_batch()` splits on whichever binds first.

Six providers are registered: `anthropic`, `openai`, `google`, `openrouter`,
`deepseek` and `qwen`. Only the first three have batch job APIs.

**Credential isolation.** The OpenAI-compatible providers each declare their own
`env_vars` and refuse to construct without a key of their own. `openai.OpenAI()`
falls back to `OPENAI_API_KEY` from the environment when none is passed, so a
missing vendor key would otherwise transmit the user's OpenAI secret to a third
party's base URL.

**Structured output** is per-provider: Anthropic takes `output_config.format`
where the API will compile the schema, and the prompt alone where it will not
(`anthropic_provider.py`, v0.5.9);
OpenAI, Qwen and OpenRouter use `json_schema` with `strict: true`; Gemini takes a
`response_schema`; DeepSeek supports only loose `json_object` mode, so
`supports_json_schema = False` and the schema reaches it through the prompt.

**Cache layout** is the reason the request type is shaped the way it is. Caching is
a byte-exact prefix match, so anything volatile appearing before the breakpoint
destroys the hit rate:

```
system    [historian instructions + operation instructions + JSON schema]  <- breakpoint
user      [example 1 prompt]
assistant [example 1 JSON]
user      [example 2 prompt]                    (few-shot: one user/assistant pair
assistant [example 2 JSON]                       per example; breakpoint on the last)  <- breakpoint
user      [the topic, or the JSON being fixed]                                (volatile)
```

The provider is resolved from the model ID via `pricing.provider_for()`, so a
single call site can mix providers per pipeline phase. A model ID containing `/`
(e.g. `anthropic/claude-sonnet-5`) routes to OpenRouter.

**Few-shot examples.** An `AtomSpec`'s `example` accepts a
single filename or a list. Every example sits inside the cached prefix, so extra
examples cost roughly a tenth of what they would uncached — and they push the
prefix past the cache minimums that atoms would otherwise fall short of. The
history pack registers two examples for every base atom. `city` was the last on
one: the corpus has no seed-shape `City` to promote — every stored city is
post-expand — so `sardis.json` was authored by hand rather than
drawn from the corpus the way the other second examples were. Order must stay
stable, since the prefix is matched byte for byte. `LLMCall` normalises both forms and validates each
example against the atom's model; the older per-provider subclasses consume only
the first and log a warning saying so.

`llm_classes/provider_call.py` bridges the two layers: `ProviderCall` and
`ProviderCallAugment` keep the `LLMCall` contract so they can be dropped into
`llm_call_mapping`, while routing the actual request through here. One pair covers
every provider, and their request is `build_request`'s,
the batch builder's (§2.2).
