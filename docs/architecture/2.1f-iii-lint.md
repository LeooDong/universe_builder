### 2.1f-iii-b Contradicting identity files — `lint.alias_contradictions`

`aliases.txt` and `not_duplicates.txt` are mirrors: one says "these spellings
are one topic", the other "these atoms are not, whatever their names suggest".
Nothing checked that they agree, and they did not. Three groups asserted an
identity a human had explicitly refused:

```
aliases.txt         Dipylon Krater = Dipylon Amphora = Dipylon Vase
not_duplicates.txt  Dipylon Krater != Dipylon Amphora
                    # A krater and an amphora, both from the Dipylon cemetery.
```

**The asymmetry is what makes it dangerous.** `not_duplicates.txt` gates only
`universe_builder duplicates`, while `aliases.txt` drives the grouping every work list and
resolver reads — so the alias wins and the refusal is silently overridden by the
file that was supposed to respect it.

And a contradiction is self-extending. `_merge_into_alias_file` folds a new pair
into any group sharing a name, so an honest later line joins the false group and
inherits its claim: adding `Dipylon Amphora = Dipylon Vase` grew the bad group
rather than starting a clean one. All three originated in one machine-written
batch, which is the general risk — `duplicates --apply` and `lint --apply-review`
both write identity lines, and neither consulted the refusals. Now the
writer does: a line that would join two whole spellings a `!=` line keeps apart
(directly, or by merging into a group through a shared head or parenthetical, as
`Irbid (Arbela)` joined `Erbil = Arbela`) raises and nothing is written. Whole
spellings only, so a refusal between `Thebes (Luxor)` and `Thebes (Boeotia)`
does not forbid `Thebes = Luxor`.

The check reads both files from **whichever alias path is in force**, since
`load_aliases` honours the `ALIASES_LIST` override and reading the refusals from
a different directory would compare unrelated files.

It runs for every atom type like any other check and `run` collapses the
identical copies, rather than suppressing itself for all but the pack's first
atom — which is what it did first, so that `universe_builder lint --check alias-contradiction
--atom artifact` answered "No findings" having compared nothing. Restricting to
an atom type is ordinary, and a linter reporting clean without running is the one
output it must never produce.

Absent refusals are a different case and are *not* an error: no
`not_duplicates.txt` means no refusals, so none can be contradicted and clean is
vacuously true — the medications pack has no such file. It is logged anyway,
because a mis-set `ALIASES_LIST` produces identical silence.

### 2.1f-iii-c Disowned topics — `lint.topic_drift`, `universe_builder lint --check topic-drift`

The index call decides the several hundred topics every later phase generates,
and it is the one call whose mistakes nothing downstream can see. Asked for a
topic that does not exist, `create` does not fail — it writes a schema-perfect,
factually accurate atom about something else. Egyptian History listed **`Berlin
Gold Hat of Tutankhamun`**, an object that has never existed; the create pass
wrote an entirely correct atom about the *Berlin Gold Hat*, a Central European
bronze-age cone in a Berlin museum, and filed it under Egyptian history.
Validation cannot catch that: the payload is valid and the prose is true.

The only trace is that the atom declined to call itself what it was asked about.
So the check compares the topic in the filename against the name the atom
declares, and reports the gap — filtered by what the gap contains:

| topic | atom calls itself | verdict |
|---|---|---|
| `Berlin Gold Hat of Tutankhamun` | `Berlin Gold Hat` | **drift** — attribution dropped |
| `Shroud of Turin (believed to be connected with Egypt)` | `Shroud of Turin` | **drift** — relevance claim refused |
| `Nicaea (Iznik)` | `Nicaea` | fine — a second name for one city |
| `Tomb of the Unknown Soldier in Athens` | `Tomb of the Unknown Soldier` | fine — a location, not a claim |

Two signals qualify a gap: the dropped words argue for the topic's own relevance
(`believed`, `contains`, `associated`), or they **trail the topic immediately
behind a connective** (`of`, `by`, `from`). The second is what catches a bare
fabrication like `of Tutankhamun`, which contains no arguing word at all. It has
to be the *immediately preceding* word — counting everything after any `of`
flagged `Tomb of the Unknown Soldier in Athens`, where Athens is where the tomb
is rather than whose it is.

Removal is reversible and has **three** parts. The atom moves to `_offtopic/`
(moved, never unlinked); the topic comes out of the index atom — leaving one
without the other means the next `create` run regenerates it, the same trap the
alias lines exist for in `universe_builder duplicates`; and **`universe_builder index` must be re-run**,
because the `links.json` index keys edges and provenance by content id and keeps
pointing at atoms that are no longer on disk until it is rebuilt. The index atom
is backed up beside the removed atom as `<name>.before`, because it is the most
expensive file in the corpus and `data/` has no undo.

Note what the rebuild does *not* clear: `provenance` is derived from the
append-only journal rather than from disk, so it still records that the removed
atom was written, on the date it was written. That is history, not staleness —
the write happened, and the journal is the one thing in the system that cannot
go stale.

### 2.1f-iii-d Shared aliases — `lint.shared_aliases`, `universe_builder lint --check shared-alias`

The duplicate finder reads the names atoms declare about themselves, which makes
it only as good as those declarations. Two atoms that both list a name **no atom
is called** look like one subject to it:

| alias | claimed by | actually |
|---|---|---|
| `Hierakonpolis Palette` | Narmer Palette, Two Dog Palette | two objects, one findspot |
| `Great Harris Papyrus` | Papyrus Harris I, Papyrus Harris 500 | two documents |
| `Usermaatre Setepenre` | Ramesses II, Ramesses IX, two reign events | a throne name, over-claimed |
| `Nikaia` | Nicaea, Nice | two cities, one etymology |

`overbroad_aliases` (check 1) cannot see these. It compares a claim against
other atoms' `name.common`, and here nothing owns the name, so there is no
collision to find. The blind spot is precise and it is where false merges come
from: `universe_builder duplicates` proposed both of the first two rows as resolvable pairs.

**Why this matters more than an untidy field.** `universe_builder duplicates --apply` retires
the losing atom *and* appends a line to `aliases.txt`, and that line is what stops
the next `create` run from regenerating the distinction. A wrong merge is not a
file to move back — it is an identity the corpus can no longer express.

The check is corpus-wide rather than per-type, because the collisions cross
types: `Usermaatre Setepenre` is claimed by a person and by the event of their
reign. Two files for *one* subject are left alone — that is a duplicate, and
`universe_builder duplicates` adjudicates those.

**The pre-fill deliberately never proposes `same`.** `suggest_verdict`'s
containment and similarity rules are calibrated for check 1, where the rival
atom really is called the alias; run over this check's findings they proposed
`same` for `Construction of Djoser's Step Pyramid` claiming `Step Pyramid of
Djoser` (an event and the artifact it produced) and for `Sinai and Palestine
Campaign` claiming `Sinai Campaign` (1915 and 1956). `suggest_shared_verdict`
offers only the safe direction: `wrong` where the subject is an action on the
thing the alias names (`Reign of`, `Construction of`, `Discovery of`), which
drops the claim from that atom alone and leaves every rival to its own row.
Everything else stays `?`, because an unfilled row costs a reading and a wrongly
filled one costs an identity.

Two properties the review file depends on, both fixed after a review gate
caught them:

- **Evidence is keyed by `(file, alias)`, never by file.** An atom claiming two
  shared aliases has a different rival for each; a file-keyed map hands the
  first to both rows. Since the header tells the reviewer to treat `DISAGREES`
  as strong, a mismatched pair argues for the wrong verdict rather than merely
  confusing.
- **A dry run names every removal.** `wrong` is the only verdict that deletes,
  and it was the only one the dry run summarised as a count while printing the
  additive `same` lines in full — the destructive half was the unpreviewable
  half, against a `data/` with no undo. It now prints `remove: <file>: <alias>`
  per row.

**Verdicts can be pre-filled from Wikipedia** — `universe_builder lint --check shared-alias
--review FILE --via wikipedia`. The test is redirect equality: two spellings
that reach one article are one subject; two that reach different articles are
not; anything else abstains. Free, no key, no model. The
resolver is the **history pack's**, not core's: `domains/history/wikipedia.py`
is handed to core through `DomainPack.identity_resolvers`, and `--via` offers
whatever the active pack declares (medications declares none, and the flag
says so). The same holds for `sources --via`, and **`sources` has no default
for a pack with no free resolver**: the paid `search` path must be named. Core
carries the review-file mechanics and the contested-name rule; which
encyclopaedia a domain trusts is the domain's.

Three methods were scored against 25 hand-adjudicated rows before choosing:

| method | right | wrong | abstained |
|---|---|---|---|
| redirect equality | 13 | **0** | 12 |
| article text contains the alias | 18 | **7** | 0 |
| intro text contains the alias | 18 | **7** | 0 |
| search-capable model (on the 12) | 9-10 | 2-3 | 0 |

Text matching fails because an article names relatives, successors and
predecessors — *mentioned* is not *is*. The model failed differently and worse:
it assigned Ramesses VI's princely name to Ramesses V while sounding certain.
Redirect equality abstains on Egyptian throne names, which are not article
titles, and that is the whole reason it is the one chosen: half the rows decided
with no observed error beats all of them decided with a quarter wrong, because
`same` writes a permanent identity into `aliases.txt`.

**An adjudicator named by `--via` answers alone — there is no fallback.** The
first wiring let the string rules fill rows where Wikipedia abstained, which put
three rows in a `--via wikipedia` file reading `same` under the note "resolves to
a disambiguation page": the heuristic had overridden a refusal while keeping its
wording, so the row looked adjudicated by a source that had said no. Two were
`Apollonia`, which names half a dozen cities — applying them would have declared
one generic name identical to two of them, then aborted the whole review on the
chained-alias guard. An abstention now stays `?`, carrying its reason.

A second rule covers names the first cannot resolve: where two subjects contest
a name and Wikipedia holds them as **separate articles**, the name describes both
and identifies neither — `Bab al-Nasr` and `Bab al-Futuh` both claiming `Gate of
Victory`. Applied bare it strips the name from every contestant including its
real owner, so a subject whose own article states the name keeps it; the same
pass still strips `Usermaatre Setepenre` from `Ramesses IX`, whose prenomen is
*Neferkare* Setepenre.

That veto is **tri-state, and it has to be**: states / read-and-absent /
unread, with only the middle permitting a deletion. Two-state fails open —
`subject_leads` blanks an entire batch of twenty when one request fails, so a
single transient error would have deleted twenty contested names on evidence
never obtained, indistinguishably from articles that genuinely omit them.

The resolver side has the same rule (v0.1.20, from the
pack's fix): `resolve_titles` answers `(None, landed, False)` for a name the
source looked up and found no page for, and **leaves out** a name it could not
look up, so absence reads as unknown (`.get` with an abstaining default). The
contested-name rule takes `answered=` and abstains when the shared alias was
not answered: "no page" says the alias is nobody's own article, "no answer"
says nothing.

On the live corpus it decided a share of the rows and disagreed with the human
adjudication on none already filled. Scored separately against the pairs in
`not_duplicates.txt`, which a human had declared different, it gave **no false
`same`**: every other row agreed or abstained.

On the corpus, a few of the findings were mechanically pre-fillable. Applying
those plus a couple adjudicated by hand removed both known false merges from
`universe_builder duplicates`.
