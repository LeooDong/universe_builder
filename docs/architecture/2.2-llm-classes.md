### 2.2 LLM layer — `src/universe_builder/llm_classes/`

A thin adapter, not a provider implementation. `execute_prompt.py` expects the API
call to happen during construction; this layer keeps that contract while the actual
request goes through `providers/`.

`LLMCall` is the abstract base and does everything provider-independent: resolves
the output path through `store`, loads and validates the configured examples,
derives the JSON schema from the atom class, validates the reply, and writes the
file or the `_ERROR` sentinel.

| Class | Used for |
|---|---|
| `ProviderCall` | create — resolves the provider from the model ID |
| `ProviderCallAugment` | fix / verify / expand / append |
| `OllamaCall` | local `http://localhost:11434/api/chat`; experimental, and the local context is too small in practice |

The augment class takes three extra arguments — `augment_to_json` (the existing file
contents), `topic` and `user_instructions` — which is what separates a
from-scratch generation from an operation on an existing file.
(`include_json_schema`, stored and never read, went in v0.3.0.)
`user_instructions` carries per-call detail that must not enter the cached prefix;
the expand pass uses it to name the single period it is expanding.

**One prompt builder**. `ProviderCall.build_request`
delegates to `providers.requests.build_request`, the batch builder, so a phase
sends the same prompt synchronously as in a batch. The operations name the
operation (`operation="fix"` and so on; create's default needs none) and create
passes its `context`; `LLMCall` keeps both, and `OllamaCall` accepts and ignores
them. The system text is the pack's persona, then `The context is {context}.`,
then `prompts/operations/<operation>.txt`, joined by blank lines; the
`base_system_text` a call is handed is no longer read by `ProviderCall` (only
`OllamaCall` builds its own prompt from it). The user turn is
`"{prompt_start_text}'{subject}'"`, then (augment) `"The subject is {topic}.
Here is the JSON to work on:\n{payload}"`, then the per-call instruction or
create note. Expand and append serialise their payload as the batch path does
(`json.dumps(data, ensure_ascii=False)`, not `indent=4`). Only `custom_id` (the
subject) and `metadata` (no `operation`/`target` routing) remain the sync
path's own; `tests/test_golden_prompts.py` pins sync and batch equal but for
those. Before this the two paths differed — sync create quoted the subject as
`f"{start} '{subject}'"` (two spaces before the quote), sync fix/verify sent
the operation text alone with no persona and no examples, sync augment dropped
`prompt_start_text`, put the instruction before the payload and joined with
`\n`. Batch produced almost the whole corpus, so batch was the reference. An
A/B (verify and fix on the balanced tier, sync transport for both, a blind
strong-tier judge on every pair) found the batch prompt no worse: every reply
valid in both arms and both phases, no truncation or re-asks, a judge split
that slightly favoured the batch prompt, and a small rise in cost per item for
the extra input tokens (persona and examples), partly offset by fewer output
tokens. The defensive topic strip
`ProviderCallAugment._system()` applied, and its `stable_system_text=`
override, went with the old builder: nothing per call reaches the system text.

**The four per-vendor classes are gone**. `OpenAICall`,
`OpenAICallAugment`, `ClaudeCall` and `ClaudeCallAugment` each reimplemented
transport, and each got prompt caching wrong: the augment pair interpolated the
per-file topic into the cached system block, and `ClaudeCall` left the one-shot
example after the last breakpoint. `OpenAICall` also hard-coded `temperature=0.2`,
which every gpt-5 model rejects with a 400 (B9), and used loose `json_object` mode
rather than an enforced schema. Everything they did correctly is done by
`providers/`, which is tested directly in `tests/test_providers.py`.

Naming and paths belong to `universe_builder/store.py` — see §2.1b.
