### 2.2b Pipeline config and CLI, continued — running a phase

**`--dry-run` is the reason the CLI exists.** It resolves the same configuration
the real run would, prints which model each phase would use and why, and lists
the work it would attempt — reading the filesystem and calling nothing.

`execute_prompt.run_phase` is the single-phase entry point behind it. It returns
a process exit status: non-zero when a phase produced no successful result at
all, so a scripted run can tell "nothing to do" from "everything failed".


**All six phases now run.** `PHASES` offered six choices and `run_phase`
implemented four — `--phase create` and `--phase index` (then `history`) reached
"Phase %r is not runnable on its own yet" and exited 2, reachable only through
`main()`. Both are implemented (`_run_history`, `_run_create`). `main()` and
its `run_*` helpers were deleted in v0.3.0; `universe_builder
run --phase P` is the only synchronous entry.

The dry run was wrong for exactly those two phases: it printed
`(topics from HISTORY_list.txt)` and a work count of **1**, when a full create is
**461** subjects. `--dry-run` exists so a run's cost is knowable before paying
for it, so under-reporting by two orders of magnitude was worse than not
offering it.


**Phases name a capability tier, not a model.** `frontier` / `strong` /
`balanced` / `economy`, resolved through the active provider's table in `pipeline.yaml`.
Model ids turn over every few months, so a config full of them is a config that
is always slightly wrong, and switching vendor meant rewriting every line — it is
now `defaults.provider` or `--provider`. A phase may still name an exact model
id, which passes through untouched: pinning one phase to reproduce a run must not
mean abandoning tiers everywhere else. `resolve_model` reports both layers, so a
dry run explains a model that appears nowhere in the config:

    create  ->  gpt-5-nano  (phases.<phase> -> tiers.openai.economy)

Four tiers rather than five, because every extra tier is a judgement someone has
to make per vendor and vendors ship roughly three useful sizes. `strong`
(v0.1.18) exists because OpenAI now ships a fourth: gpt-6.1-sol at $2 / $10
per million, between the balanced model and gpt-6-astra ($10 / $50),
the price a second-opinion judge can afford where frontier cannot. OpenAI's
balanced is gpt-6-luna ($0.10 / $0.50) since v0.1.19, newer than gpt-5.6-luna
and half its price. A model id is part of an atom's filename, so an atom
re-created under the new model is a second file beside the old one: correct an
atom by retiring it (`retire`) and letting create fill the gap, never by
creating over it. A vendor
with nothing in that gap maps it to its frontier model, never below balanced.
`tests/test_tiers.py` checks each provider defines all four *and that they are
ordered by price* — a table that gets that backwards silently puts the bulk pass
on the expensive model.

`config.PROVIDER_MODELS` is derived from the tier tables and the pricing table
rather than written out (every priced model since v0.5.9),
because a hand-maintained copy is a second registry to keep in step:
`test_config.py` caught `gpt-6-astra` priced and tiered but uncallable the moment
tiers landed, and that check only works if there is one source.

`execute_prompt.model_for_atom()` is the single resolver `run_phase` uses. The
legacy `main()` helpers (deleted in v0.3.0) once resolved separately and
disagreed: they indexed `PHASE_MODELS`, which is phase-level only — so
`atoms.person.create` applied through `universe_builder run` and was silently
ignored by `python -m universe_builder.execute_prompt`.

`run_batch --model` also accepts a tier name, since a config that speaks tiers
makes `--model economy` the natural thing to type. Without it the failure landed
inside the pricing table — *"'economy' is not in the pricing table"* — which
points at the wrong problem entirely.

**Per-atom overrides (`atoms.<atom>.<phase>`) were documented, implemented, and
unreachable.** `cli.cmd_run` resolved once with `atom=None` — which never matches
an atom override — and handed the single answer to `run_phase` for every atom
type, so the feature only worked when you passed `--atom`. `run_phase` now
resolves per atom type, the CLI passes `--model` through *unresolved*, and the
dry run prints a per-atom table whenever the answers differ.
