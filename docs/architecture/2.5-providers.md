### 2.5 Provider layer — `src/universe_builder/providers/`

**`complete()` streams, and that is not an optimisation.** A non-streamed request
holds an idle socket for the whole generation and something in the path closes it
at roughly 60 seconds, so the synchronous pipeline could not produce *any*
response that took longer — on any model. Diagnosed on a `history` atom on
`gpt-6-astra`, which takes minutes: every attempt failed with
`RemoteProtocolError: Server disconnected without sending a response` just past
the minute. The identical request with `stream=True` succeeded. The
batch path was never affected, because its results are fetched from a file rather
than held on an open connection — which is why batch was reliable all day while
sync was not.

Streaming brings two failure modes the single-response path did not have, and
both are handled in `OpenAIProvider.complete`:

- **A stream can end early without raising.** The iterator simply runs out. If
  the cut lands after the last brace the partial JSON parses, validates, and is
  written as a *good* atom with `Usage()` zeros making the call look free —
  `ok=True`, `error=None`, 0 tokens. A stream that ends without a `finish_reason`
  is therefore refused, and its partial text kept as evidence.
- **Usage arrives on a final chunk carrying no choices**, so
  `stream_options.include_usage` must be set or every cost silently reads zero.
  A missing usage chunk is logged as *unknown, not zero*.

The assembled text goes through the same `_validate` as before, so truncation
reporting and schema handling are unchanged.

**A refusal has to survive the layer above.** `ProviderCall.call_llm_api` returns
the raw text on failure so the `_ERROR` file gets the payload, and
`LLMCall.parse_response_to_pydantic` then validated that text *on its own terms* —
which overturns the provider whenever the text happens to parse. For a schema
failure the two agree; for a cut stream they do not, and the pipeline wrote a
2,402-byte atom and reported `outcome: ok` one frame after the provider logged
"treating it as incomplete". `LLMCall.provider_error` now carries the verdict, and
`parse_response_to_pydantic` honours it rather than re-deciding. **Validity of the
text was never the question the provider answered** — it answered whether the text
is the *whole* response.

**One retry loop, with a clock.** `providers/run.py` holds a module-level
`Policy` — transport and validation attempts, backoff, and a per-attempt
client-side timeout — installed by the entry points from `pipeline.yaml`'s
`retry:` block via `run.configure()`. The `--config`-selected file is the one
that governs: `cmd_run` threads its config path into `run_phase`, which
installs that file's policy and resolves models from the same file
(`model_for_atom(config=…)`). The first version re-read the default file for
both inside `run_phase`, so an alternate config governed the dry-run display
and the journal while the run itself obeyed a file the user had pointed away
from. Two things made this necessary. The
block was *displayed* by `universe_builder config` and applied by nothing —
`run.complete` hardcoded its own attempts, so the file promised three and the
code did what it liked. And no client-side timeout existed anywhere, so the
OpenAI SDK's 600s default read timeout ran with its own 2 internal retries
nested invisibly inside our 3 attempts — roughly half an hour before our
retry logic saw a dead call. The SDK's retries are now off for the
synchronous call (`max_retries=0` via `with_options`, in
`OpenAIProvider._sync_client` and the Anthropic `complete`), so
`run.complete` is the only loop and it logs every attempt; the policy timeout
rides `LLMRequest.timeout` into the SDK per attempt. On a streamed call it
bounds the wait *between chunks*, so a 182s generation is untouched while an
idle socket fails in `timeout_seconds` rather than ten minutes. Batch
endpoints keep the SDK's retries: uploads and polls sit outside
`run.complete` and a retried upload costs nothing. The Google provider is
not covered — its SDK takes timeouts differently and the provider is still
unexercised.

An alternative transport path that sits beside `llm_classes/` rather than
replacing it. Where `LLMCall` couples prompt assembly, transport and file IO into
one constructor, this layer separates them, which is what makes batch inference
and correct prompt caching possible.

| Module | Responsibility |
|---|---|
| `types.py` | `LLMRequest`, `LLMResponse`, `Usage`, `BatchHandle`, `BatchStatus`. `LLMRequest` splits content into a stable prefix (`system`, `examples`) and a volatile suffix (`user`). |
| `base.py` | The `Provider` contract: `complete()` plus optional `submit_batch()` / `poll_batch()` / `fetch_batch_results()`. Also holds the strict-JSON-schema normaliser, `system_with_schema` (the system text plus "Return JSON matching this schema exactly:" and the schema, which all three providers send byte for byte alike) and `_validate_stored`, every provider's collect-path validation (v0.2.0; every provider passes its stop signal since v0.4.0, so a truncated line is named as truncation; a `refusal` is named as a refusal since v0.5.9). A provider without batch raises `errors.BatchNotSupported`, which is also a `NotImplementedError`, from `batch.submit` too. |
| `requests.py` | Pipeline-aware request building. Reads the active domain pack (`atom_mapping`, the pack's `base_system` and `examples_dir`) and `prompts/`, and decides what is cacheable. Paths resolve through `universe_builder.settings`, so it is working-directory independent. |
| `run.py` | The synchronous retry loop and its `Policy` (attempts, backoff, per-attempt timeout), installed from `pipeline.yaml`'s `retry:` block by the entry points via `configure()`. The only retry loop on the sync path — SDK retries are off there. Since v0.5.9 an SDK error whose HTTP status says a retry cannot help (`NOT_RETRYABLE_STATUS`: 400, 401, 403, 404, 413, 422) is returned at once, and a `retry-after` header (429, Anthropic's 529) sets the floor of the backoff, capped at `backoff_max_seconds`. |
| `anthropic_provider.py` | `messages.stream` (v0.5.9; `messages.create` before, whose non-streamed call the 120s policy timeout cut off on a thinking model, and the SDK refuses above ~21K `max_tokens` unstreamed) and `Provider._validate` on the joined text blocks, so an invalid reply keeps its raw text and truncation and refusal are named (v0.1.20). The schema goes as `output_config` through the SDK's `transform_schema` (the API 400s on `minimum`/`maximum`); a schema the API will not compile ("The compiled grammar is too large": most history atoms, on the first live run) is remembered per (model, schema) and sent through the prompt only, the reply's Markdown fence or prose stripped (`_json_text`), and, since v0.6.0, closing braces or brackets after a complete object dropped with a warning (`_without_extra_closers`: Haiku 5.5 added one `}` to several prompt-only Discovery replies live; anything else after the object still fails); `submit_batch` probes each new pair once with a one-token call. `max_tokens` is held to the model's `max_output`. Batch `custom_id`s outside `^[A-Za-z0-9_-]{1,64}$` (a slug with "é", or past 64 characters) go out under a wire id and come back under their own (`extra["wire_ids"]`); an errored line names the nested API error. Two cache breakpoints; Message Batches. |
| `openai_provider.py` | `json_schema` + `strict: true`; automatic caching via content order; Batch API via JSONL upload. Also hosts the three OpenAI-compatible providers — `OpenRouterProvider`, `DeepSeekProvider`, `QwenProvider` — which are the same client against a different base URL. |
| `google_provider.py` | Gemini with `response_schema`; relies on implicit caching because explicit caches bill storage per hour. |
| `batch.py` | Submit, poll and collect. Handles persist to `<data_dir>/_batches/` so a batch survives process exit; a handle is moved to `collected/` once its results are safely written, and missing-result reports go to `missing/` — both subdirectories, so neither is in the handle glob. |
| `pricing.py` | Model registry, cost estimation, cache-minimum warnings, and `max_output` (the output cap, recorded for the Anthropic rows from the Models API). Table lives in `model_pricing.json`. `effort: false` on a row (v0.6.0) marks a model that takes no effort setting (gpt-4o-mini, gpt-4.1, gpt-4.1-mini, Haiku 4.5); `effort_levels` replaces the provider's levels for one model (how an OpenAI model is let take `xhigh` once verified; no row does yet). `task_budget: true` (v0.6.1) marks a model that takes Anthropic's task budget (Fable 5.1, Opus 5.5, Opus 5, Opus 4.8, Sonnet 5; not Sonnet 5.5 or either Haiku; Fable 5 and Opus 4.7 take one too but have no row). |
| `effort.py` | The provider-neutral reasoning effort (v0.6.0): `validate` (`low`, `medium`, `high`, and `xhigh`/`max` passed through), `wire` (what a provider sends, from its `Provider.EFFORT_LEVELS` or the model row's `effort_levels`: OpenAI `reasoning_effort` or `reasoning.effort`, `low`/`medium`/`high` and `xhigh` only where a row lists it, never `max`, Anthropic `output_config.effort` merged beside the format with all five; none for Google, DeepSeek, Qwen, OpenRouter or an `effort: false` model, warned once per model; a lacking level raises `errors.EffortNotSupported`, a 400 that `run.complete` does not retry), `sent` (what goes on the wire for a model, via `registry.provider_class`, no client built: what everything records), `refusal` (the CLI's pre-flight on the same rule), `label`/`split_label` (`model@effort`) and `add_argument` (the one `--effort` flag). |
| `task_budget.py` | Anthropic's task budget (v0.6.1): `validate` (a whole number, at least `MINIMUM` 20,000), `wire` (what a provider sends, from its `Provider.TASK_BUDGET`: none, warned once per model, for every provider but Anthropic; for Anthropic, `errors.TaskBudgetRefused`, a 400 that `run.complete` does not retry, for a total under the minimum, a model whose `model_pricing.json` row lacks `"task_budget": true`, or a total over the `max_tokens` the request sends unless `LLMRequest.allow_task_budget_over_max_tokens`; a warning once over two thirds of `max_tokens`), `sent`/`sent_or_none`/`of_request` (what goes on the wire, no client built: what everything records), `refusal` (the CLI's pre-flight), `output_config` and `add_argument` (the one `--task-budget` flag, for a pack's own verbs too). |
| `util.py` | `expected_custom_ids()` — reconciling what a batch returned against what was submitted. |

**Task budget on the wire** (v0.6.1). `LLMRequest.task_budget` (validated,
not part of `cache_key`) is the carrier and `Provider.task_budget_for`
asks `task_budget.wire`, against `Provider.sent_max_tokens` (Anthropic's is
`max_tokens` held to the model's `max_output`). The Anthropic provider
merges `{"type": "tokens", "total": N}` into `output_config` beside `format`
and `effort`, and `_betas(params)` reads it back: with a budget the call goes
to `client.beta.messages.stream(..., betas=["task-budgets-2026-03-13"])`
(the streamed call and the prompt-only fallback alike) and a batch to
`client.beta.messages.batches.create(betas=..., requests=...)`, the handle
recording `extra["betas"]` so `poll_batch`/`fetch_batch_results` use the beta
batches endpoints with the same header; without one, every call and handle
is what it was. The schema probe stays on the plain endpoint. The budget
is **advisory**: the model sees a countdown and paces itself; `max_tokens`
stays the hard per-response cap. Size it by measuring the task; for a single
call keep it under `max_tokens` with headroom (one half to two thirds of
it); only an agent loop a pack drives itself, where one budget spans
several responses, may exceed `max_tokens`
(`allow_task_budget_over_max_tokens`). Recorded as sent: `sent_task_budget`
on attempt lines (sync `_support._record` from
`ProviderCall.sent_task_budget`, a create failure, batch `_journal_result`
from the handle's `extra["task_budget"]`, `journal.record_call`), in the
envelope only when set; none for a provider that ignores it. `costs` gains
no grouping. **Note for packs**: a verb that builds its own `LLMRequest`
(the history pack's `index-append`) passes `task_budget=` and a `max_tokens`
that leaves room (the engine's bare `DEFAULT_MAX_TOKENS`, 16,384, is under
the 20,000 minimum, so a budget beside it is always refused).

**Effort on the wire** (v0.6.0). `LLMRequest.effort` (validated, not part of
`cache_key`) is the one carrier; `Provider.effort_for(request)` asks
`effort.wire`. **What is recorded is what was sent** (`effort.sent`, from
the model's provider class, no client built): journalled as `sent_effort` on
every attempt line (sync `_support._record` from `ProviderCall.sent_effort`,
a create failure, batch `_journal_result` from the handle's
`extra["effort"]`, which `batch.submit` stamps with the sent value,
`journal.record_call`), and in the envelope only when set. An effort asked
of Gemini, DeepSeek, Qwen, OpenRouter, gpt-4o-mini, gpt-4.1 or Haiku 4.5 is
recorded as none, so `costs --by effort` shows the wire.
Before v0.6.0 nothing was sent: OpenAI's reasoning models ran at the API
default reasoning effort (not recorded here), Claude at the model's default
(`high` on Haiku 5.5 and Sonnet 5.5, `medium` on Opus 5.5).
