### 2.1f Work lists — `src/universe_builder/topics.py`

Where a create run's subjects come from. `execute_prompt.run_base_atom_calls`
(deleted in v0.3.0) and `run_batch._subjects_from_history` each walked the History atoms with their own
code and **disagreed**: the batch one de-duplicated across files, the pipeline
one did not. Both now call `topics.from_history()`.

**Synonyms are grouped, not split.** Ids are hashed from the exact string, so
`Thebes` and `Thebes (Luxor)` are two atoms for one city — and a second model
over the same civilisation reliably produces the other form. An exact-match
dedup therefore accumulates *duplicates* rather than coverage. `alias_keys()`
treats a trailing parenthetical as a declared alternate name, which is how this
corpus already writes them (`Hierakonpolis (Nekhen)`, `Narmer (Menes)` — 24
stored entries), and `group_synonyms()` collapses entries that share one.

`group_occurrences` holds each claim as a `_Declaration` (keys, folded
scope, declared names for an alias line, the contexts that made it for a
parenthetical entry, and `speaks_for(context)`), not four parallel lists
(v0.2.0). The order a group's spellings are tried for a
stored atom is `topics.lookup_order`, which `duplicates._lookup_reaches`
walks too; a name's keys, most specific first, are `_ordered_keys`, the set
of which is `alias_keys` and the sequence of which the resolver probes.

Its warnings (a name claimed by two groups of one scope, an entry that
partially overlaps an alias line) are about the files, and each atom type's
work list re-reads them, so inside one command — `cli.main` and
`run_batch.main` wrap theirs in `topics.warnings_once()` — a message is
logged once rather than once per atom type. Outside a command
every load warns.

Three properties of that grouping matter, and each exists because the obvious
version was wrong:

- **The entry declaring the link can arrive last**, so a single pass over
  `[Thebes, Luxor, Thebes (Luxor)]` leaves `Luxor` alone — nothing had linked it
  when it was seen.
- **Groups never chain.** Union-finding over every shared key merged
  transitively: `["Memphis (Mit Rahina)", "Mit Rahina (Saqqara)", "Saqqara"]`
  collapsed to one topic and **Saqqara vanished**, joined to Memphis through a hop
  neither entry claims. So a parenthetical entry forms its own group and is never
  merged with another; bare names attach to the group that names them, and a name
  claimed by two different declarations is left alone and logged. Merging wrongly
  costs a topic that is never generated again and nothing points at the gap;
  splitting wrongly costs a duplicate that `--gaps` reports.
- **Any read that decides whether to keep a record is guarded.** These run
  inside loops over whole folders, and an unguarded read costs the caller every
  record behind the bad one — sorted order deciding which. The shape recurred
  four times in a day (`_history_files`, `has_real_atom`, `_submit_payload_batch`,
  the fix/verify loop), each time because a guard was added at one call site and
  the next was written without it. **A file that cannot be read is treated as
  absent**, which keeps the topic queued for regeneration rather than silently
  skipping it.
- **The form with a *real* atom wins.** `store.atoms_for` counts files, not
  usable content, so an `EmptyModel` placeholder from a failed generation made a
  failure outrank a validated atom. `topics.has_real_atom` is the single
  judgement, shared with `status --coverage` — the two were separate and
  disagreed.

A declaration is identified by the *pair of names it declares*, not its own
spelling: `Amarna (Akhetaten)` and `Akhetaten (Amarna)` are one claim, and the
same entry appearing in two History atoms is agreement rather than conflict.
Observed on the real corpus: cities grouped onto existing atoms,
`Heliopolis (Iunu)` yielding to the stored `Heliopolis`.

**The alias file — `domains/history/aliases.txt`.** Data-declared links have two
gaps: nothing connects names no entry writes together (`Akhetaten` /
`Tell el-Amarna`), and once a second civilisation loads, one name can mean two
places (`Thebes` in a Greek list must not join the Egyptian `Thebes (Luxor)`).
The second gap is closed structurally: **no claim crosses a civilisation
boundary unless an alias line says so.** A data declaration speaks only for
the Histories that made it (the same pair declared by two Histories is
agreement, and serves both), so with no line at all a foreign bare name
stands alone — a visible duplicate at worst, never an invisible merge. The
alias file, parsed by `topics.load_aliases()`, is then the deliberate
instrument for both directions, in one line-based format:
`Canonical = Other = Another` declares a group (first name is the spelling
generated when no stored atom decides otherwise) — written globally it joins
across civilisations, which is how Alexandria in two Histories stays one
city; and a `[Civilisation]` section scopes the lines under it to topics
from that History — inside its civilisation a scoped line outranks every
other claim (giving Greek `Thebes` its own `Thebes (Boeotia)` identity), and
outside it it claims nothing. One claim outranks even a matching scoped
line: an entry that declares its own pair is captured only by a line
*containing* that pair, because the entry is more specific about itself than
a line that merely shares a name — a Greek History listing the Egyptian city
as `Thebes (Luxor)` keeps it, rather than surrendering it to the Greek
`Thebes (Boeotia) = Thebes` line (found by review before it shipped: the
first version merged the Egyptian city into Boeotia, silently). Emitted rows
are finally de-duplicated on the normalised topic, since equal normalised
topics are one content id and one file. Its groups join `group_synonyms`' pass as
first-class declarations: a parenthetical entry whose declared pair falls
entirely inside one alias line folds into it as a restatement, while a partial
overlap stays a rival claim — agreeing on one name while adding another is the
transitive chain that once lost Saqqara, so it goes to the ambiguity rule
(kept, warned) rather than merging. `prefer` searches the group's *declared*
names too, so a list saying only `Akhetaten` resolves onto a stored
`Amarna (Akhetaten)` no current list spells out; two stored atoms inside one
group are warned as the duplicate the line exists to prevent. A missing alias
file means grouping runs on declared links alone — exactly the pre-file
behaviour — and an unreadable one degrades to the same, loudly. The seed lines
already earn their place on the real corpus: `Hermopolis (Khmun)` and
`Hermopolis Magna (Khmun)` are different pairs sharing `Khmun`, which grouping
rightly refused to guess about and warned on every run until a line said they
are one city.

**A quoted name is one literal name** (v0.4.0). A trailing parenthetical in an
alias line splits like any other, so a line naming the event `Unification of
Upper and Lower Egypt by King Menes (Narmer)` also claimed `narmer` — and a
global line is read for every atom type, so the person `Narmer` became
ambiguous and was queued for create again. Written `"Unification of Upper and
Lower Egypt by King Menes (Narmer)" = Unification of Upper and Lower Egypt`,
the name claims its whole spelling and nothing else: `AliasGroup.names` keeps
the quotes (a rewrite of the line keeps them), `_ordered_keys` returns the
one key, `name_key` folds the quotes away, and `AliasGroup.spellings` /
`topics.unquote` give the spelling to hash, prefer and generate (pass 3 and
`duplicates`' spelling lookups use it). Pass 1 lets an entry whose whole key
is a quoted name of a line that speaks for its context declare no pair, and
pass 2 hands it to that line outright (`AliasGroup.literal_keys`,
`_Declaration.literals`) — a line sharing only its head or inner name is no
rival. Straight double quotes around the whole name only.

**One parser per identity file** (v0.1.20).
`alias_files.py` holds the only parser of each file — `parse_alias_text`
(`Declaration`: line number, raw text, body, names, scope, provenance) and
`parse_distinct_text` (split on every `!=`) — wrapped as `AliasFile` and
`NotDuplicatesFile`, and the only path resolvers: `aliases_path()` (the
`ALIASES_LIST` override, else the pack's) and `not_duplicates_path()` (always
beside the alias file in force). `topics.load_aliases`, `duplicates`'
readers and writers and `lint.alias_contradictions` all read through it. It
folds nothing; callers fold the names it returns with `topics.alias_keys`.
Readers and **writers** alike resolve through it: `duplicates.apply`,
`write_distinct_lines` and `lint.apply_review` used to take the pack's own path
and ignore the override, so under a test `workspace` they could reach the real
`aliases.txt` (fixed v0.1.20).
Both writers replace the file in one step (`alias_files.write_atomically`:
temp file + `os.replace`, permission bits kept) rather than truncating or
appending in place, so a crash mid-write cannot leave a partial identity file
(v0.1.20, 1.3).

**Create notes** (v0.1.15) answer the problem the alias file cannot: a
spelling that is one topic but means something lesser-known than the bare
name suggests. The create prompt carries only the name and the context, so
the model takes the famous reading — history's `Later Han dynasty`, listed
among the Five Dynasties, came back as the Eastern Han. The pack's
`create_notes_path` (`type | subject | note` lines, sectioned by context like
the alias file, `*` for any type) adds one sentence to that one subject's
user turn, on the synchronous path (`create_atom` → `ProviderCall`) and both
batch doors (`run --batch`, `run_batch submit`), via
`topics.create_note(type, subject, context)`: this type in this context, then
any type in it, then this type anywhere, then any. Every other request is
byte for byte what it was, and the note never enters the cached prefix.
Unlike the alias file, a malformed or missing declared file is an error
(`CreateNotesError`): a note that silently fails to load is a misgeneration
paid for twice. `settings.CREATE_NOTES` overrides the pack's file, as
`ALIASES_LIST` does, and the test `workspace` points it at an empty one.

**List neighbours** (v0.1.16) do the same without anyone writing a note: with
`DomainPack.create_neighbours = k`, a subject's create prompt names the k
entries either side of it in its context's index list
(`topics.list_neighbours`, via `create_instructions`, which puts them before
the note in the one user turn). The index list knows what an ambiguous name
means by the company it keeps, and the bare prompt threw that away: known
history misgenerations re-created bare mostly came back wrong again; with
three neighbours either side, nearly all came back right, and the controls
stayed right. The subject is found in the list by the work list's
own grouping (`ListIndex.position`: the entry `group_occurrences` assigns to
that survivor), never by a shared name — v0.1.16 matched by name and put the
Ottoman `Foča` at the Greek list's `Phocaea (Foça)`, a different topic.
Only the first listing frames a create, so a name two lists mean differently
still needs a scoped alias line. `topics.ListIndex` reads each index list once
per batch; `settings.CREATE_NEIGHBOURS` overrides the pack, and the test
`workspace` sets 0.

It happens **on the work list and never in `store.normalise_topic`**, which feeds
the content id — joining names there would re-point every id and orphan all 453
stored atoms. `near_matches()` is the looser, *advisory* counterpart used by
`status --coverage --gaps`: it may guess, because a wrong suggestion costs a
reader two seconds while a wrong grouping silently merges two real places.

De-duplication is not tidiness. Two civilisations can both list Alexandria, and
content-addressed ids map one subject to one path — so a duplicate is two calls
racing for a single file, the collision `operations._support.persist` exists to
survive, and the second call is paid for to write what the first already wrote.

Each `Topic` keeps the context it came from, because the context reaches the
model: `build_request` puts `The context is {context}.` in the **system** text,
which is the cached prefix. That is why `by_context()` exists and why the batch
path submits **one batch per (atom type, context)** rather than one overall — a
batch spanning two civilisations carries two prefixes and neither request group
reads the other's cache entry. First occurrence wins for a shared subject.

**One topic, one file, whichever path generated it.** This is the point of
content-addressed ids, and `batch._output_path` states it directly —
but it was once false. `create_atom` appended
`" (context: {atom_name})"` to the subject before handing it to `LLMCall`, which
slugs *and hashes* the atom from that string, while the batch path hashed the
bare subject. One topic had three identities:

| derived by | id for "Hieroglyphic writing" |
|---|---|
| batch path (bare subject) | `h931c34c8003af691` |
| synchronous `create_atom` | `h495688e995974e14` |
| the corpus rename, from the slug on disk (deleted v0.3.0) | `h79200bea7bdbdfe4` |

The suffix was redundant in the prompt too — `prompt_start_text` already reads
"Provide a response for the discovery or invention commonly known as" — so it was
removed at source rather than worked around. Both paths now produce
`discovery_h931c34c8003af691_hieroglyphic_writing_gpt-5-nano.json`, confirmed by
generating the same topic each way.

Every file generated before the migration carried a `_context_<atom_type>` tail
in its slug. The rename recovered each exact subject with the tail stripped
and rebuilt the slug from it, so every move landed on exactly the name
`store.path_for` produces for the bare subject; its contested names (empty
sentinels against real atoms, one genuine `Cleopatra VII` pair) were triaged
by hand. The rename code — `rename_plan`, `apply_rename`, the
link-then-unlink resume and its `_same_file` guard — was deleted in v0.3.0 with
the `migrate` verb. `topics._context_of`
strips the same tail so the model is not told "The context is egyptian history
context history!".
