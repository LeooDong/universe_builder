### 2.1e Run journal — `src/universe_builder/journal.py`

An append-only record of every attempt, and the structural answer to a bug that
would not stay fixed.

**Why it is wired in.** It was first built and deliberately left inert,
because B8 — "a failed fix destroys its own evidence" — had been closed far more
cheaply by `store.commit_fix`. Before long B8 had recurred **four
times**, each through a different write path:

1. the original fix pass deleting the sentinel it had just read
2. `persist` writing an `EmptyModel` over the atom's own path
3. batch `collect` writing a repair to the sentinel, then clearing it
4. batch `collect` replacing the sentinel with the repair's own failure

That is a pattern, not four coincidences. The `_ERROR` sentinel is both the work
queue and the only copy of the evidence, and every new write path eventually
writes over it. Each fix stopped one route; none of them stopped the next. The
journal is append-only, so no later write can destroy an earlier payload — a
sentinel lost to a fifth route becomes an inconvenience rather than the end of
the record.

**Layout**, one directory per run, under the generated-data directory::

    <data_dir>/_runs/<run_id>/
      run.json                        # resolved config, provenance, code revision, models
      journal.jsonl                   # one line per attempt
      attempts/<attempt_id>/
        request.json                  # exactly what was sent
        response.raw.txt              # exactly what came back, BEFORE any parse
        response-envelope.json        # provider metadata, usage, ids
        replaced.json                 # the bytes an in-place rewrite replaced (v0.3.2)

`_runs` is underscore-prefixed deliberately: `store.iter_atoms` skips
underscore-prefixed directories, so journal data can never be walked as corpus
data.

**What ran.** `run.json` carries `provenance`: the engine's
distribution and version (`importlib.metadata`, plus `imported_version` when
the imported `__version__` disagrees), and the active pack's name, registering
module and distribution (`registry.pack_provenance`, via the
`universe_builder.domains` entry point of a pack that installs this engine, or the
engine's own distribution for a bundled pack). `code_revision`, in `run.json`
and on every line, is the engine's git commit **only when it runs from its own
checkout** (`journal._engine_checkout`: a src-layout root with `.git` and a
`pyproject.toml` naming `universe_builder`), else None. It used to be
`git rev-parse HEAD` in `settings.REPO_ROOT`, which under a wheel is
site-packages, so git answered for whichever repository enclosed it — a pack
that keeps its venv in its own checkout recorded the pack's HEAD as the
engine's revision. Runs from before carry no `provenance`
key; `journal.run_provenance` returns None for them and nothing else changes.

**How it is wired.** `journal.start_run()` is called by the entry points —
`cli.cmd_run`, `run_batch.main` for `collect` only (submit no longer opens an
empty run), `execute_prompt.main`, and the three paid core verbs
`collisions --via model`, `duplicates --via model` (they once
called `provider_run.complete` with no run open, so `costs` never saw
them) and `sources --via search` (v0.1.20); `restore --apply` opens one for its own
mechanical line (v0.3.2) — and `journal.current()` returns the active run.
Those three share one setup, `cli._paid_setup` (v0.2.0):
`--config`, the tier resolved against `--provider`'s table (`openai-search`'s
for `sources`), the retry policy installed, the spend announced, then the run
opened with the resolved model in its config. Each takes `--model`, `--config`
and, where a vendor choice means something, `--provider`. Outside a run, `current()` returns
a `NullJournal` that records nothing, so the library stays usable and tests need
no setup. Threading a journal through every operation signature was the
alternative, and it would have meant changing every call site of every operation
to carry something most of them do not otherwise care about.

Three recording points, each chosen as the one place the relevant path passes
through holding both the raw payload and the verdict:

| path | recorded in |
|---|---|
| synchronous | `operations._support.result_from_call` |
| batch | `providers.batch._journal_result` |
| a core verb's own model call (`collisions.adjudicate`, `duplicates.triage`, `sources --via search`), or a pack verb's | `journal.record_call` (takes `target_pointer` and `schema_id` since v0.2.0, for a call whose answer is written to a file) |

All three swallow their own exceptions. Journalling is observation, and a failed
observation must never cost the run the result it was observing —
`TestJournallingNeverBreaksARun` pins that.

There is a **fourth** recording point that is easy to miss and was: every
operation catches transport errors and returns `Result.failed` *before* reaching
`result_from_call`, so a call that died before its first byte left no entry at
all — the atom invisible to the record and absent from `needs_fix()`. That is the
worst case for the queue to be wrong about, since a transport failure is exactly
what a retry fixes. `_support.record_failure` is called from the `except` branch
of **all five** operations — `expand` is easy to miss, because its failure path is
per *period* inside a loop rather than around the whole call — with
`validation_stage="transport"` and `retryable=True` when the cause is
`providers.errors.TransportFailed`, and `validation_stage="call_setup"`,
`retryable=False` for anything else raised building the call (an example that
does not validate, a missing key). Since v0.1.20 the
synchronous adapter **raises** `TransportFailed` once `providers.run.complete`
reports every attempt failed (`LLMResponse.transport_failed`): before, it
returned `{"error": "<exception text>"}` as if the model had answered, which was
written as an `_ERROR` sentinel and journalled as a payload, so a batch fix
(which, unlike the sync pass, did not skip `{"error": ...}` placeholders) paid
to "repair" a 401. Batch fix now skips them as batch verify does; create
regenerates the topic.

**The atom type it is given must match the one the call itself uses**, or a single
atom gets two work-item ids depending on how it failed, and a retry queued under
one never settles the other. `create`, `fix` and `verify` pass
`config.atom_name`; `append` and `expand` pass `config.augment_atom_name`.
`append` originally passed `atom_name`, which filed a failed *append* against the
city it supplements — marking a good city as needing repair while the append that
actually failed went unrecorded. `TestBothFailurePathsAgreeOnTheWorkItem` checks
the pair per operation.

**"Nothing arrived" is not an empty payload.** `record_attempt` refuses
`raw_payload=None` without a reason precisely to keep "the model returned
nothing" apart from "we never heard back". `Result.raw_text` defaults to `""`,
so the first wiring passed that through and recorded
`raw_payload_available: True` — a claim to hold bytes that do not exist — beside
a reason saying nothing came back. The call sites now pass `raw_text or None`,
and `record_failure` passes `None` with the error as the reason.

**Two design decisions worth knowing.** `record_attempt` takes `raw_payload` as a
*required* keyword and writes it first — before the request, before the envelope,
before the journal line, and at the call site before `json.loads` and before
Pydantic. There is deliberately no overload that attaches the payload afterwards,
because that is the version that loses the bytes exactly when they are malformed.
`NullJournal` keeps the same required keyword for the same reason: a stub that
accepted the call without it would let a call site forget the argument and still
pass its tests.

And resolution is an *append*. `outstanding()` replays entries in sequence order
rather than filtering, because a work item can cycle `needs_fix` → resolved →
`needs_fix` when a repair itself fails; a filter returns the stale first attempt
in that case. Work items are keyed on the content id (`journal.work_item_id`), so
a fix attempt and the create attempt it repairs are one item even though one
wrote an `_ERROR` name and the other did not.

**Reading spend back out.** `universe_builder costs` (§ the command table) aggregates these
attempt events; the journal is the cost database and nothing else stores one.
Two limits are structural rather than incidental. **Older synchronous
attempts can record no usage at all** — most of them successful, because the
synchronous path once did not capture usage; the tokens were never written
down, so no report can recover them and a corpus-wide total is a floor. And
**older batch work cannot be attributed to its phase**:
those attempts are journalled by the `collect`, hours or days after the submit,
under a run whose recorded command is `collect`. The handle always routed each
request's `operation` (`requests.build_requests`), and `_journal_result` now
records it on the entry, so `costs --by phase` reads `verify (batch)` straight
off it. Older entries lack the field; `expand` and `append` survive that
because they generate under prefixed atom types, but a batch-collected
`create`, `fix` and `verify` all write a base atom type with the base schema
and nothing in those entries distinguishes them. `costs` labels that bucket
`create/fix/verify (batch)` rather than guessing.

**A mechanical write is journaled, and is not a call** (after v0.3.0). A pack verb that rewrites an atom with no model — history's
`retire-list`, `fold-history`, `respell-urls`, `periods --apply-labels`,
`period-polities` — journals the write so the atom's provenance shows it, as
an attempt line, through `journal.record_mechanical(operation, atom_type,
path, what, kind=)`: `execution_mode: "mechanical"`, no payload (`mechanical
<kind>, no model involved: <what>` in its place), no model, no usage,
validation `ok`. `costs` leaves such lines out of every row, total and footer
and prints them as one count ("N mechanical write(s)"). The pack wrote these
lines by hand before the API existed, unmarked, and `costs` counted them as
unpriceable sync calls under the usage-gap footer — most of a corpus's
"no usage" attempts. `journal.is_mechanical` recognises
those by shape (no model, provider, usage, payload or failure stage, and
validation `ok`; a model call names its model and a transport failure is
`failed` with a stage), so no journal is rewritten.

**When the work targets an existing file, the id comes from its filename.**
Subjects reaching an augment pass are read off the filename, and slugs are
lossy: `Boutros Boutros-Ghali` slugs to `boutros_boutros_ghali`, which hashes
to a *different* id. On the first live batched-fix cycle that split one repair
across two work items — queued under the true subject's id at create, settled
under the slug's at collect — so the queue kept a repaired item. The filename's
`h…` token is the id the true subject would hash to, so
`journal.work_item_from_path` is authoritative wherever a target exists:
`_support._record` derives from the call's `response_path`,
`record_failure` takes a `target=`, and `batch._journal_result` uses the routed
target. A failed *verify* or *expand* additionally records no `work_status` at
all — its target is still a valid atom, and a `needs_fix` there would send the
fix pass to overwrite good data. The rule holds on every failure route:
validation failures via `_record`, transport failures via `record_failure`
(their retry is the pass run again, not a repair), and the batch collect path
via the routed `operation` — which also writes no sentinel for a failed
verify.

**What is not yet wired.** The fix pass still takes its queue from the `_ERROR`
glob, not from `needs_fix()`. The journal now records the same information
alongside it, and `universe_builder status` prints both counts and flags a disagreement.
The disagreement can point either way: more sentinels than journal items means
failures predating the journal or an overwritten record; more journal items
means a lost sentinel — or, in older journals, a repair recorded under a
mismatched id. Switching the queue over is a control-flow change and is
tracked separately.

**An in-place rewrite keeps what it replaced** (v0.3.2). Every write over an
existing atom on behalf of a model call saves the bytes it replaces, exactly,
into the journal attempt's folder as `replaced.json` and records
`replaced_ref` and `replaced_sha256` on the line (both measured, so in
`DERIVED_FIELDS`). Not `input_sha256`: that is the call's input, and on the
batch path the input was read at submit while the bytes replaced are whatever
sits at the target at collect — the gap where a correction made in between
was silently reverted. The mechanism is `record_attempt(replaces=path)`
(also on `record_call(replaces=)` and `record_mechanical(save_replaced=True)`),
called before the write; a path that does not exist saves nothing, and it must
be the line's own `target_pointer`. Who passes it:

| write | line that keeps the bytes |
|---|---|
| sync verify, create (over a file already at the path), append (over an unmerged append file) | the call's attempt line, via `result_from_call(replaces=call.response_path)` — only when the result validated |
| batch collect of create/index/fix/verify | the batch line, `_journal_result(replaces=out)` when the result is ok |
| expand, sync or batch | one mechanical `expand` line of kind `splice`, from `operations.expand.write_expanded` — one copy per city rewrite, not one per period call |
| append's merge into the base atom | one mechanical `merge` line, from `operations.merge.merge_json_files` |
| `universe_builder restore` | one mechanical `restore` line — so a restore can itself be undone |

Fix saves nothing: `store.commit_fix` never writes over an existing atom, and a
sentinel promoted to a new atom replaces nothing (the sentinel's own bytes are
the failing attempt's raw payload, already journaled). A create of a new file
saves nothing either. One copy per rewrite is the whole disk cost.
`journal.replaced_bytes(entry)` reads the copy back and checks its hash — None
for a line that saved nothing and for every line before v0.3.2, `ValueError`
for a mismatch and `FileNotFoundError` for a missing copy, because a restore
from evidence that is gone or altered must not quietly restore something else.
`journal.find_attempt(attempt_id, run_id=None)` finds a line across runs.
`restore.plan`/`restore.apply` and the `restore` verb (§2.2b's table) are
built on the two; `apply` refuses without an open journal run, since the
journal is the only place the bytes it replaces are kept. The filename keeps
its model suffix after a rewrite by a different model: ids do not depend on it.

**Target pointers are relative to the data dir** (v0.1.20).
`Journal._new_entry` stores every `target_pointer` inside the data dir relative
to it (`journal.relative_pointer`), whoever passes it — the passes, batch
collect, a pack's own verbs; one outside is kept as given. Readers go through
`journal.target_path`, which joins a relative pointer to the current data dir
and takes an absolute one (every line up to v0.1.19) as written. Before, a
copied or moved corpus had `reconcile_fix_queue` follow absolute pointers and
restore sentinels into the original.
